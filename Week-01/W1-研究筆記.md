# Week 1｜大腦核心：LLM 選擇與參數設定（LLM & Config）

> 本筆記整理 Week 1 目前最後理解到的知識，供複習使用，並非最終繳交版。原始想法與操作歷程保存在 [W1-學習歷程](W1-學習歷程.md)。

## 1. LLM 在 Agent 中的角色

### 知識｜目前理解

- LLM（Large Language Model）可以理解與生成自然語言。
- 在客服型 Agent 中，可以協助理解使用者問題並產生回答。
- 模型本身能力強，不代表一定知道特定企業或情境需要的正確資訊；能取得哪些資訊也會影響回答。

此處只記錄 Week 1 的理解，不提前展開後續 Knowledge / RAG 單元。

## 2. 模型選擇

### 知識｜選擇原則

**模型不是越大、越強就一定越適合。**

選擇模型時應考慮：

- 任務複雜程度
- 模型能力
- 成本
- 回應速度
- 是否符合實際需求

如果簡單任務使用能力遠超需求的模型，可能造成不必要的成本與資源使用。

目前形成的選擇思路：

> 任務需求 → 所需能力 → 選擇適合的模型 → 再考慮成本與速度。

## 4. Parameter（模型參數）

### 知識｜目前理解

- Parameter 是模型在訓練過程中學習到的數值，例如 weights 與 biases。
- B = billion；7B 約代表 70 億個 parameters，70B 約代表 700 億個 parameters。
- Parameter 數量較多通常代表模型容量較大，有能力學習更複雜的模式。
- **Parameter 較多不代表結果一定比較準確。**
- 模型表現還會受到訓練資料、模型架構、訓練方式、任務等因素影響。
- 小模型本身不代表「比較專精」；若經過適當訓練或微調，才可能在特定任務上有很好的表現。

### 正式來源查證

[Google Machine Learning Glossary](https://developers.google.com/machine-learning/glossary) 的 parameter 與 model capacity 詞條，分別支持「訓練中學習到的 weights 與 biases」及「模型容量通常隨參數數量增加」的理解。這不等於 parameter 越多，在特定任務上就一定越準確。

## 5. 蒸餾模型（Knowledge Distillation）

### 知識｜目前理解

- 由較小的模型學習較大模型的部分能力。
- 目標是在較小模型容量下，盡可能保留大模型的能力。
- 可以用「老師模型／學生模型」協助理解：較大的模型是老師，較小的模型是向老師學習部分能力的學生。

### 正式來源查證

[Google LLMs: Fine-tuning, distillation, and prompt engineering](https://developers.google.com/machine-learning/crash-course/llm/tuning) 的 Distillation 段落說明：較小的 student model 透過 teacher model 提供的輸出學習其知識。這與我「用小模型學習較大模型部分能力」的理解相符。

蒸餾模型通常能降低推論所需的計算資源，但不代表結果一定完全等同 teacher。這是資料查證，不是我已完成蒸餾實驗的結果。

經典研究補充：[Google Research — Distilling the Knowledge in a Neural Network](https://research.google/pubs/distilling-the-knowledge-in-a-neural-network/)。本週僅補充來源，不展開公式或訓練方法。

## 6. Temperature

### 知識｜目前理解

- Temperature 不是耗能設定。
- 它主要影響生成內容的隨機性與多樣性。
- 較低：通常較穩定、保守。
- 較高：通常有較大的生成多樣性。

### 實驗觀察

使用 GPT-4o，以相同 Prompt 比較 Temperature = 0 與 Temperature = 2：

> Give me three ways to back up my computer files.

兩次的核心答案仍相當接近。因此不能僅根據這一次實驗認定 Temperature 對所有問題都會產生巨大差異。

### 實驗限制

兩次測試位於同一對話，且 context rounds = 3，因此前文可能影響後續回答。比較參數時，也需要控制對話 Context。

## 7. Response max length

### 知識｜目前理解

- 控制單次回答可輸出的最大長度。
- 不等於模型的記憶體大小。
- 設定過小時，回答可能尚未完成就停止。

### 實驗觀察

Response max length = 5，清空對話後使用 Prompt：

> Give me three ways to back up my computer files.

模型只輸出：

> Sure! Here are three

之後就停止。因此觀察到：輸出限制過小不一定會讓模型主動濃縮答案，也可能直接造成回答未完成。

### 尚未確認

本週尚未用官方文件確認 Coze 的 Response max length 精確單位，因此目前不將其單位寫成 tokens。

## 8. Context Window 與 Context Rounds

### 知識｜目前理解

| 名稱 | 目前理解 | 簡單比喻 |
| --- | --- | --- |
| Context Window | 模型整體可以處理的 Context 容量 | 桌面的總大小 |
| Number of context rounds included | Coze 在產生下一次回答時，選擇納入多少輪先前對話 | 實際拿幾疊先前對話資料放到桌上 |

**兩者不是同一件事。**此處的比喻只協助理解，不代表已驗證精確計算方式。

## 9. Coze 中的模型與免費額度

### 知識｜需要區分的概念

以下三件事情不能直接視為相同：

- 帳號有免費 Credit
- 模型是否被標示為 Free
- 模型本身的價格

### 實際探索與觀察

本週在 Coze Model Selection / Model Management 實際看到多種 OpenAI 與 Gemini 模型。

Free filter 顯示 Results 0，但實際仍能利用帳號 Credit 執行模型，因此「免費額度」不等於「免費模型」。

## 10. 本週核心知識關係

```text
任務需求
↓
任務複雜度
↓
需要的模型能力
↓
模型選擇
↓
成本 / 速度 / 效果的取捨
```

- 模型大小（parameters）會影響模型容量，但不是準確度的唯一因素。
- Temperature、Response max length、Context 等設定，則會影響模型實際生成回答時的行為。

## 11. 與數位鑑識的初步連結

### 尚未驗證的推論｜應用假設

- 較單純的資料整理／基本摘要工作，可能不需要使用能力最強、成本最高的模型。
- 需要分析多份資料與進行較複雜推理的工作，可能需要能力較強的模型。
- 因此未來若真的設計數位鑑識相關 Agent，不同工作階段可能適合不同模型。

以上只是學習後形成的應用假設，不是已經實際驗證的結論，也不是已完成的 Agent 設計。

## 12. 數位鑑識業務流程｜2026-09-23 補充

### 正式資料支持的核心流程

NIST SP 800-86 Section 3 與 Figure 3-1 的核心 forensic process 為：

> Collection → Examination → Analysis → Reporting。

目前依資料整理的理解：

- Collection：取得資料時，需要注意資料完整性與 chain of custody。
- Examination：偏向辨識、擷取、整理相關資訊。
- Analysis：利用 Examination 的結果回答調查問題。
- Reporting：記錄處理過程與結果。

來源：[NIST SP 800-86](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-86.pdf)，詳細使用範圍見 [W1-Sources#6. NIST SP 800-86｜數位鑑識業務流程](W1-Sources.md#6-nist-sp-800-86數位鑑識業務流程)。

### 依資料整理的較大學習架構

為理解「完整業務流程」，將準備與後續管理一起納入學習：

```text
案件需求／調查問題
↓
權限、程序與技術準備
↓
Collection
↓
Examination
↓
Analysis
↓
Reporting
↓
證據保存／後續管理與流程改善
```

**這是依資料整理出的學習架構，不是 NIST 官方七階段模型。**

### 個人延伸思考｜Reporting

我認為報告除了結果，也應說明使用的技術／模型與可能偏差。其中「AI 模型與偏差揭露」是我的延伸思考，不應寫成 NIST 的固定規定。

## 13. Examination 輔助 Agent｜目前構想與界線

### 個人構想｜尚未驗證

目前希望 Agent 根據調查問題，從大量已取得的數位資料中，推薦「值得優先人工查看」的項目並說明理由。Agent 不直接做案件結論，推薦是否合理仍由使用者判斷。

### 目前縮小後的可實作範圍

| 項目 | 目前構想 |
| --- | --- |
| 輸入資料 | 簡單、虛構且已整理好的檔案紀錄，如檔名、時間、路徑、裝置活動 |
| 使用者輸入 | 調查問題 |
| Agent 輸出 | 值得優先人工查看的項目與推薦原因 |
| 回饋方式 | 由使用者判斷推薦是否合理 |
| 暫不實作 | 真正的鑑識工具、磁碟映像解析、複雜 API |

此範圍是為了符合現階段能使用與測試的條件，不代表已完成實作或取得驗證結果。範圍縮小與模擬選擇的思考過程保存在 [W1-學習歷程#16. 數位鑑識業務流程與 Agent 連結｜2026-09-23](W1-學習歷程.md#16-數位鑑識業務流程與-agent-連結2026-09-23)。

### 與 LLM Selection 的連結｜應用假設

簡單的大量資訊整理與較複雜的多線索理解，可能需要不同模型能力。因此模型選擇應依任務需求，而不是一律使用最大、最強的模型。

**上述鑑識輔助任務與模型能力的對應尚未實際驗證。**
