# Week 1｜大腦核心：LLM 選擇與參數設定（LLM & Config）

> 學習歷程 checkpoint：保存真實學習過程，並非最終繳交版。

## 1. 一開始對模型選擇的想法

### 原始想法

情境：模型 A 能力較強、較昂貴、較慢；模型 B 較小、便宜、快速，但能力較弱。

我的原始想法：

> A，雖然初期成本可能較高，但較強、較好的模型通常能夠使用較久、不易被時代淘汰；反之，較小、較便宜的版本可能初期成本較低，但後續的維護成本以及時代、技術的更替都可能導致其淘汰，產生更大的替換成本。

### 想研究的問題

> 一開始選能力較強、價格較高的模型，長期來看真的會比使用較小、便宜的模型更划算嗎？

## 2. 一開始對 LLM 在 Agent 中角色的理解

### 原始理解

> 我其實沒有概念，但以客服 Agent 的案例來看，我認為可能是理解問題並提出可能解決方案。

### 新的理解

後來理解到 LLM 主要負責理解與生成語言，但能否正確提出解決方案還會受到它能取得的資訊影響。

## 3. Gemini 模型與價格探索

### 實際探索與觀察

我查看 Gemini 官方模型頁面，比較 Gemini 2.5 Pro、Flash、Flash-Lite。

我的觀察：

> Pro 是最先進的模型，適合處理複雜任務，但是花費時間可能較長，若非複雜任務可能浪費過多效能；Flash-Lite 模型速度較快，適合處理簡單問答及任務，複雜內容可能較容易產生錯誤；我認為 Flash 較適合一般日常需求。

### 查看價格後的想法改變

接著查看官方定價後，我的想法改變為：

> 看到實際價格後，我認為應該先比對所需與模型提供的功能，達到模型功能利用最大化。

## 4. Parameter（參數）

### 原始理解

> 不知道。

### 新的理解

後來我的理解：

> Parameter 是模型經過訓練後，用來進行計算的數值；parameter 數量較多通常代表模型容量較大，因此有能力學習較複雜的模式與處理較複雜的任務，但不代表結果一定比較準確。

### 理解的修正

我曾認為較小模型可能因為比較小而比較專精，後來修正為：
模型較小本身不代表比較專精；如果經過適當的訓練或微調，小模型才可能在特定任務表現很好。

## 8. Temperature

### 原始理解

我一開始以為：

> Temperature 可能和模型運作時的耗能有關。

### 新的理解

後來理解：
Temperature 主要影響生成內容的隨機性與多樣性，而不是耗能。

### 實際實驗

我使用 GPT-4o，以相同問題：

> Give me three ways to back up my computer files.

**Temperature = 0：**
回答主要包含 External Hard Drive、Cloud Storage、Built-in Backup Tools。

**Temperature = 2：**
回答主要包含 External storage devices、Cloud backup services、Automatic backup software。

### 觀察與實驗限制

我的觀察：

> 我覺得差異沒有我想像中的大，可能是問題不太複雜的關係，答案的多樣性相差較少。

但後來發現這次 Temperature 實驗存在限制：
兩次測試在同一對話環境進行，而且 Number of context rounds included = 3，因此前文 Context 可能影響第二次結果。

這讓我發現之後比較模型參數時，除了 Prompt 與參數之外，也需要控制對話 Context。

## 9. Response max length

### 原始理解

一開始我認為：

> 可能是記憶體大小或輸出容量。

### 新的理解

後來理解它比較接近限制單次回答能輸出的最大長度，而不是模型記憶體大小。

### 原始預測

> Response max length 降低後，ways 可能會減少。

### 實際實驗與結果

實際把 Response max length 設為 5，並清空對話後，以相同問題測試。

模型只回答：

> Sure! Here are three

之後就停止。

### 與預測不同的發現

因此實際結果與我的預測不同：
模型並不是主動減少回答的項目，而是回答在尚未完成時就受到輸出長度限制而停止。

## 10. Context

### 原始理解

一開始我認為 Number of context rounds included 是：

> 模型一次能跑幾份不同的資訊。

### 新的理解

後來理解：
Number of context rounds included 是 Coze 在產生下一次回答時納入多少輪之前的對話。

另外區分：

- Context Window = 模型整體可以處理的 Context 容量。
- Context rounds = Coze 選擇放入多少輪之前的對話。

## 12. 模型選擇觀念的改變

### 重新選擇與理由

重新面對「較強昂貴模型 vs 較小便宜模型」時，我後來選擇較小的模型，理由是：

> 這些問題不涉及複雜的計算與任務，不需要用到太大的模型容量。

### 我的 Week 1 核心結論

> 根據需求的複雜程度選擇適合的模型，而不是單純講究模型要大要強，容易造成效能過剩，也較沒效率。

## 13. 與數位鑑識的連結

### 假設情境

假設數位鑑識 Agent 有兩個工作：

- A：將大量檔案按照圖片、影片、文件、壓縮檔等基本類型整理並產生簡單摘要。
- B：根據多份案件資料、檔案內容與時間資訊，分析不同證據之間可能的關聯。

### 我的判斷與理由

我的判斷：

- A 選較小、便宜、快速的模型。
- B 選較大、推理能力較強的模型。

理由：

> 工作 A 的任務較簡單單純，不需要複雜的思考模型；工作 B 的任務內容需要進行分析推理，適合較大、推理能力較強的模型。

目前數位鑑識是個人探索方向，不代表已經確定為期末 Agent。Digital Life Support 也只是目前學習 Agent 元件的實作載體。

## 16. 數位鑑識業務流程與 Agent 連結｜2026-09-23

### 老師要求的方向

先理解數位鑑識業務流程，再思考 Agent 可以優化的位置；同時考慮現在是否能實際使用、測試並取得回饋。

### 研究前對完整流程的理解

研究前，我對完整流程的理解大約是：

> 設備與技術知識準備 → 確認需要哪些資訊及目前設備／技術限制 → Collection → Examination → Analysis → Reporting。

### Collection：從時間紀錄到資料完整性

我原本認為 Collection 時需要注意資料存取時間與檔案修改歷史；研究後才進一步理解資料完整性與 chain of custody 的重要性。

### Examination 與 Analysis：原始區分與修正

我的原始區分是：

> Examination 主要提出事實，Analysis 根據得到的資訊進一步做分析。

研究後，我修正為：Examination 偏向辨識、擷取、整理相關資訊，Analysis 再利用這些結果回答調查問題。

### Reporting：我的延伸思考

我認為 Reporting 除了結果，也應該說明過程中使用哪些技術／模型，以及可能有哪些偏差。

**其中「AI 模型與偏差揭露」是我的延伸思考，不是 NIST 的固定規定。**

### 正式流程與較大的學習架構

NIST SP 800-86 的核心 forensic process 是：

> Collection → Examination → Analysis → Reporting。

為了理解老師所說的「完整業務流程」，我們另外整理出較大的學習架構：

> 案件需求／調查問題 → 權限、程序與技術準備 → Collection → Examination → Analysis → Reporting → 證據保存／後續管理與流程改善。

**這是依資料整理出的學習架構，不是 NIST 官方七階段模型。**正式資料與整理範圍見 [W1-Sources#6. NIST SP 800-86｜數位鑑識業務流程](W1-Sources.md#6-nist-sp-800-86數位鑑識業務流程)。

### 我目前最感興趣的 Agent 介入位置

思考 Agent 可以介入的位置後，我目前對 Examination 最有興趣：希望 Agent 能根據調查問題，從大量已取得的數位資料中找出「值得優先人工查看」的項目並說明理由，而不是直接做案件結論。

### 模擬情境中的選擇與原始理由

在包含 USB 18:32 接入、`backup_0915.zip` 18:35 建立等紀錄的模擬情境中，我優先選擇查看第 3 筆 `backup_0915.zip`。

我的原始理由是：

> 我想知道檔案建立後內部資訊為何？

當被問到取得相關資訊後下一步想知道什麼，我的原始回答是：

> 這些資訊被需要的原因。

這裡記錄的是模擬情境中的選擇與想法，不代表已完成檔案內容檢查或真實案件分析。

### 從擴大功能到重新限制範圍

我一開始希望 Agent 還能進一步查 metadata、時間紀錄等，但後來重新限制範圍：不要做成我現在這個階段用不到或用不了的東西。

因此目前可實作版本縮小為：

- 使用簡單、虛構且已整理好的檔案紀錄，例如檔名、時間、路徑、裝置活動。
- 輸入調查問題後，由 Agent 協助指出值得優先人工查看的項目並解釋原因。
- 最後由使用者判斷推薦是否合理。
- 真正的鑑識工具、磁碟映像解析、複雜 API 等暫不實作。

這是目前縮小後的實作構想，不代表已經完成或驗證。

### 連回 Week 1 的 LLM Selection

不同鑑識輔助任務的複雜度不同，因此模型選擇應依任務需求，而不是一律使用最大、最強的模型。簡單的大量資訊整理與較複雜的多線索理解，可能需要不同模型能力。

**這目前是應用假設，不是已驗證結論。**後續仍要考慮能否實際使用、測試並取得回饋。
